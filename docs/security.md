# Границы безопасности vertov-dl 0.1.0-alpha.2

Версия предназначена для одного доверенного администратора через SSH-туннель. Не публиковать API в интернет: multi-user isolation, полноценный sandbox и аудит ещё не завершены.

## Доступ

Ключ 24+ символов (рекомендуется token_urlsafe(32)) читается из файла секрета или окружения. HMAC-сессия с TTL 12 ч, HttpOnly, SameSite=Strict. Ключ не хранится в localStorage и query string. Изменяющие запросы с посторонним Origin отклоняются; тело ограничено 16 КиБ (для /api/cookies — 2 МиБ JSON при файле до 256 КиБ), вход ограничен по частоте. Все пользователи с ключом имеют одинаковые права.

Для HTTPS включить secure_cookie; по умолчанию HTTP предназначен для loopback-туннеля. Host network не даёт сетевой изоляции. Приложение слушает только loopback. Из контейнера Nginx Proxy Manager loopback хоста напрямую не доступен.

## Исходящие запросы

Все Python socket connect в task разрешены только к loopback gateway. Gateway проверяет каждый CONNECT, включая redirect/CDN, запрещает private/reserved/multicast/tunnel IPv6 и порты кроме 80/443. Смешанный DNS-ответ с внутренним IP запрещается целиком. Upstream SOCKS получает проверенный IP, поэтому повторная резолюция upstream не меняет цель. DNS выполняется резолвером хоста/контейнера, а не удалённым SOCKS DNS; его доступность важна.

Нет автоматического direct fallback. ffmpeg/ffprobe wrappers в образе запрещают сетевые протоколы; task не использует ffmpeg как downloader и принимает ограниченный набор HTTP/HLS-native/DASH протоколов. EJS/Deno использует ограниченные разрешения yt-dlp. Плагины yt-dlp отключены.

Это защита уровня приложения от SSRF, не защита от компрометации процесса/библиотеки. Python socket guard не равен seccomp/network namespace. Полный fail-closed и изолированный worker — следующий этап. Существующий VPN может маршрутизировать отдельные публичные адреса напрямую согласно своим правилам; приложение не меняет эти правила.

## Данные и ресурсы

Netscape cookies.txt проверяется до замены хранилища: до 256 КиБ и 5000 записей, строгий формат, никаких значений в ошибках/статусе. Cookies сохраняются только в /data/secrets/cookies.enc с AES-256-GCM, атомарной заменой, каталогом 0700 и файлом 0600 на Linux. Ключ выводится через HMAC-SHA256 из ключа доступа с отдельным контекстом media-loader/cookies/v1; смена ключа доступа требует повторного импорта. Это защита файла на диске, не от компрометации работающего сервера или одновременной утечки ключа. Worker расшифровывает записи в памяти и устанавливает их в cookiejar yt-dlp без cookiefile; открытых временных файлов и значений в spec/SQLite нет. Cookiejar соблюдает домен/путь/secure/expiry. Обновлённые сайтом cookies не записываются обратно: новый экспорт импортируется вручную. Удаление влияет на новые задачи; текущая может использовать свою копию в памяти. Ключ доступа и реальные ссылки не включаются в Git. SQLite хранит исходные URL, включая query: /data должен оставаться закрытым; полного шифрования БД пока нет. API скрывает source и пути. Progress и метаданные ограничены и не содержат CDN URL. Процессы запускаются массивом аргументов, пользовательский URL передаётся через закрытый каталог задачи.

Compose: UID/GID 10001, cap_drop ALL, no-new-privileges, read-only root, ограниченный tmpfs/CPU/RAM/PID. /data сохраняется в отдельном volume. Deadline, RLIMIT_FSIZE на Linux и периодический контроль диска дополняют лимиты; суммарный объём не ограничен жёсткой filesystem quota.

TTL может удалить файл до того, как офлайн-клиент вернётся. Удаление через UI окончательно удаляет серверный артефакт. Сохранение файла браузером не подтверждается автоматически.

## Обновления

yt-dlp и EJS закреплены в requirements.lock, Deno закреплён тегом образа. Python/Node base image tags и Debian apt не закреплены digest/snapshot; это пока не полностью воспроизводимая supply chain. Обновляется весь образ. Самообновление инструментов внутри контейнера отсутствует. Лицензии и атрибуции включены в LICENSE/NOTICE/THIRD_PARTY_NOTICES. Digest pinning и дополнительная проверка цепочки поставки остаются в roadmap.

Рабочие ссылки/черновики и ID задач сохраняются в localStorage по явному запросу пользователя для восстановления при обновлении. Это не encrypted storage; URL с приватными query остаются доступны тому же браузерному профилю. Ключ доступа и cookies в рабочее состояние не входят. Выход сбрасывает рабочее состояние.

Готовый файл удерживается во время активного HTTP-ответа. Временные failed-файлы ограничены отдельными 10 ГиБ/7 днями; активные задачи защищены от вытеснения, поэтому требуется резерв диска. Нормализация имени применяется только к браузерной выдаче, а не к серверному пути.

## Native FFmpeg: CVE-2026-8461 (issue #9)

Runtime-база переведена на python:3.12-slim-trixie. По Debian Security Tracker исправление для trixie входит в FFmpeg source package 7:7.1.5-0+deb13u1. scripts/check-native.py требует trixie, проверяет установленные ffmpeg/libavcodec61/libavformat61/libavutil59 через dpkg-query и dpkg --compare-versions, отклоняет версии ниже этого порога и смешанные версии библиотек. Проверка выполняется при Docker build, сохраняет /opt/media-tools/native-security.json и повторяется smoke-скриптом на реально собранном образе. Источник политики: https://security-tracker.debian.org/tracker/CVE-2026-8461 .

Это проверка конкретного security-backport, а не утверждение об отсутствии всех уязвимостей FFmpeg. Номер major сам по себе не доказывает наличие патча. Вредоносный образец не используется: регрессия генерирует корректный MagicYUV AVI и проверяет штатный fallback → H.264.

Protocol whitelist ограничивает сетевой доступ, но не защищает от ошибок native decoder при чтении локального медиа. Read-only root/cap_drop также не изолируют /data от worker с тем же UID. Отдельный worker без доступа к БД/секретам остаётся отдельным пунктом roadmap и не заменяет обновление FFmpeg.
